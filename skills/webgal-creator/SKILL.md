# WebGAL Creator

Use the author's language, names, key events, ending, and dialogue style. Work with a registered WebGAL project and keep the editable story, synchronization map, and staging outside the game and any public repository.

1. **Identify the project.** Use `project_list`, `webgal_status`, and `project_inspect`. Confirm the intended project, readable files, verified Terre mapping, and write-tool availability before planning any game write. Keep working on the Markdown in read-only mode if those prerequisites are missing. Use a dedicated project for tests.
2. **Deliver the Markdown first.** Draft `story.md` with stable scene and fragment IDs. Ask together about choices that affect the story, character depiction, cost, asset rights, or publishing scope. Show the user the actual Markdown for review. Follow [script format](references/script-format.md). Record their creative approval against the SHA‑256 of the reviewed file bytes. Reread and hash before preparing executable candidates or applying. Re-review affected passages when the content changes.
3. **Resolve asset readiness after script approval.** Follow [assets and staging](references/assets-and-staging.md). Confirm permitted sources before searching, preparing assets, or delegating. An exclusive source such as `res` bounds every material choice. Before generating WebGAL candidates, summarize the approved story's backgrounds, portraits and expressions, music, ambience, and effects. Compare them with verified, suitable, authorized assets. When there are unresolved gaps, explain their impact and present automatic preparation, user-supplied assets, and an explicitly simplified placeholder version in one grouped question. Honor any existing decision within its scope and start authorized automatic preparation when suitable tools are available. Keep the gate open until every planned cue is ready or its disclosed fallback is explicitly authorized. Script approval and write approval serve separate purposes and do not resolve asset gaps.
4. **Preflight batches and sample the draft.** After asset readiness, check operation count, byte budgets, source and target compatibility, and dependencies before each `change_plan` call. Use a non-committable draft for each valid batch. In the candidate preview, spot-check only changed scenes and cues, starting near the affected beat. Use `scene_validate` to investigate specific scenes or verify saved versions. Text-only revisions can reuse the existing asset decisions when they leave staging and asset requirements intact.
5. **Protect saved edits and write with MCP.** Read [sync and handoff](references/sync-and-handoff.md) before generating a local patch, resuming, or writing. Resume pending verification first. Base local changes on the saved scene and its revision. Use the bundled read-only helper to prepare precise patches. Obtain this batch's explicit Terre save and all-editor-pages-closed handoff before creating the formal plan. Get separate approval of that plan before applying it. Persist the pending record before `change_apply`. Verify the result and end the session.
6. **Verify playability and presentation quality.** Read back saved targets, run the project scan and use `preview_get_url` to run one complete Chrome playthrough of the final saved version after all batches. Verify the ending, speaker clearing and relevant staging. Capture [five or six key screenshots](references/acceptance.md#chrome-playthrough-and-evidence) during that same run. Add evidence images only for a concrete anomaly. [Review presentation quality](references/assets-and-staging.md#presentation-quality-review) against the approved story and asset plan. In the delivery, report on portraits and expressions, backgrounds, audio, visual style, and unfinished staging. Name the highest-value improvements and identify accepted placeholders. Record human playtest feedback separately. Follow [acceptance](references/acceptance.md) for release checks and evidence.

Terre installation, project creation, complex branching, live two-way sync, engine changes, exporting and publishing are outside this workflow. Game writes use the existing Write Coordinator. If the connected MCP is unavailable, use only an already authorized local connection to the same MCP service, or continue with the Markdown.
