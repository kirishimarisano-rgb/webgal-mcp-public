# webgal-mcp 下一版开发计划

**拟定版本：v0.2.0 · 状态：征求反馈**

当前候选的交付范围、Windows 验收步骤和验证结果见 [v0.2.0 候选说明](release-v0.2.0.md)。

这一版的目标：让第一次使用的人更快连上 Terre，让做游戏的人能在导出前查清问题，并验证更大的素材能否安全导入。本文是供贡献者讨论和领取任务的路线图。任务编号用于沟通，不表示已有 GitHub Issue；列出的能力也不表示已经实现。

如果你刚接触项目，请先看 [README 快速上手](../README.md)。如果你要找现有命令或安全规则，请看 [工具参考](tool-reference.md)。

## 1. 从哪里开始

现有基线是 **Windows + Node.js 24 + Codex + WebGAL Terre**。用户自己启动 Terre，MCP Server 默认只读；开启写入时，仍由用户先保存、离开编辑页，再明确交接。改动完成后，用户回到 Terre 自己预览或导出。

当前已有工程检查、单场景分析、素材导入、预览链接以及带计划、版本检查和恢复的写入流程。下一版沿用这些接口和 WebGAL 文件格式，优先让已有能力更好用。现有单文件写入上限是 1 MiB，单批总计 4 MiB；这也是大素材任务要解决的具体限制。

## 3. 连接检查与上手

### NEXT-01：把「接不上」变成下一步操作

**用户问题：** Codex 看得到 MCP，但不知道是 Terre 没启动、工程目录填错，还是忘了开启写入。

**实现范围**

- 复用 [工程读取服务](../src/service.ts) 和 [Terre 连接适配器](../src/terre.ts)。优先改善现有 `project_inspect` 或其调用说明，把已有信号整理成用户能执行的提示；有必要新增结果字段时，保留现有字段含义。
- 分别说明「工程文件能否读」「Terre 能否连」「配置的工程能否匹配」「是否开启了写入工具」「本批是否仍需要用户交接」。连通不代表可以写，返回 URL 也不代表引擎已跑通。
- 诊断结果只显示解决问题需要的内容。仍不自动启动 Terre、不搜遍磁盘、不输出私人绝对路径、剧情原文或凭据；检查本身不修改工程。

**验收**

- 可运行的 Terre 与正确工程能得到明确结果。
- Terre 未启动、端口不对或工程映射不符时，提示可区分已经确认的原因与仍需用户检查的可能原因。
- 未启用写入时告诉用户怎样开启；已启用但没有交接时仍不能写。
- 用已有 [Terre 契约测试](../test/terre.test.ts) 或 [MCP 服务测试](../test/server.test.ts) 覆盖稳定结果；只读检查前后测试工程的文件列表和内容一致。

### NEXT-02：用一个小案例教会第一次使用的人

给 README 或工具参考补一个完整的试用路径：确认连接 → 读取开场 → 让 Codex 提出一处小修改 → 用户保存并确认交接 → 应用 → 回到 Terre 预览。先尝试文档和少量示例，不新增安装器。

**可领取的贡献**

- 写一段可直接复制给 Codex 的提示词；为几个常见失败提供「看到什么 → 检查哪里 → 怎么重试」。
- 使用临时工程或可公开的原创测试素材复现。提交说明中记录实际使用的 Windows、Node、Codex、Terre 版本和对应步骤。
- 可组织一次跟读：让没有参加过开发的人只按 README 操作，记下第一个看不懂或做不下去的步骤，优先修那一步。

**完成标准：** 至少有人从干净的安装环境照文档完成连接和一次只读检查；写入演示在专用测试工程上验证。没有运行过的组合只写「未验证」。

## 4. 导出前的工程检查

### NEXT-03：一次查看整个工程的静态问题

**用户问题：** 工程场景变多后，逐个文件找缺图、缺音频和写错的跳转很费时间。

**拟交付结果**

- 一份汇总：检查了多少场景，哪些场景有问题，哪些场景由于范围或大小限制没查完。
- 每条问题提供场景相对路径、能够确定时的行号、引用的目标，以及原因。区分**确定缺失的静态引用**、**需要人工预览确认的动态引用**、**因输入或限制没检查完的情况**。
- 首版只检查已授权工程里已有的场景和本机素材引用。复用 [场景分析](../src/analysis.ts)、[工程读取服务](../src/service.ts) 和已有路径策略；不执行脚本、不请求外部 URL、不自动修复或导出。
- 报告有明确的场景数量、耗时和结果大小边界。超过边界时返回已检查的范围及未检查的原因，不能给出「工程无问题」。接口先讨论是扩展现有工具还是新增一个工程级只读工具，不要求每项诊断有单独工具。

**验收样本**

| 场景 | 预期结果 |
| --- | --- |
| 静态素材和场景跳转都正确 | 报告无已发现的静态引用问题，并给出实际扫描范围 |
| 一张图缺失、一处跳转指向不存在的场景 | 各有独立条目，能从文件和行号找到问题 |
| 路径来自变量或其他不能静态判断的写法 | 标为未能验证，不判为缺失 |
| 工程有循环跳转、中文路径或不合法引用 | 扫描能结束；不因合法中文路径误报，也不访问授权目录之外 |
| 项目超过扫描预算，或有文件无法读取 | 报告不完整并列明范围，不吞掉失败 |

有意不做可视化剧情图、孤立场景删除建议及 WebGAL 运行仿真。静态报告通过后，仍需用 Terre 预览关键路径。

## 5. 大素材导入

### NEXT-04：先验证技术路径，暂不开放生产写入

目前写入计划会保存经过编码的文件内容，详见 [Write Coordinator](../src/changes/coordinator.ts) 和 [写入限制](../src/changes/types.ts)。调高常量会同时放大内存、计划记录和故障恢复压力。本任务先用临时工程记录这些影响，再决定实施方式。

**比较两步**

1. 在当前实现上用原创样本记录基线：小于和超过 1 MiB 的素材怎样被接受或拒绝、有哪些可理解的报错。
2. 做可丢弃原型：分段读取来源，一边计算版本一边写入受控暂存文件。评估在计划中仅保存必要的来源身份、大小和版本信息的做法，以及提交时怎样核对来源仍与计划一致。记录读写耗时、峰值内存、临时磁盘开销、文件数和故障时的剩余数据。

**退出条件：** 用至少一张超过 1 MiB 的有效背景图和一段有效音频样本验证原始字节不变；给出建议上限和失败时的处理方式。上限是原型结果，不是预先承诺。原型不得接到正式写入路径或覆盖用户文件。

**建议入口：** [素材来源](../src/assets/source.ts)、[业务计划](../src/changes/business.ts)、[目标发布](../src/changes/targets.ts)、[来源保护测试](../test/changes/source-guards.test.ts)。

### NEXT-05：原型通过后，再接入现有写入工具

- 优先沿用现有素材导入操作。素材大小限制与文本、批次记录和 MCP 响应限制分开设计，避免把媒体内容塞入工具输出或日志。
- 写入必须经过同一个 Write Coordinator：用户交接、计划、来源和目标版本复核、必要的备份、提交和可核对的结果。新素材只允许创建；已存在的目标不覆盖。
- 暂存文件要能被核对，失败时必须知道哪些文件已完成、哪些没写、哪些结果还不确定；不自动重试覆盖。清理只针对本次已确认的临时产物。检查旧计划、批次日志及恢复记录的兼容性；旧会话不能继承写权限。
- 先交付背景图和 BGM 的真实 Terre 验证。视频、复杂目录或 Live2D 等独立列出支持状态，不用图片测试结果替代。

**发布前必须通过**

- 超过 1 MiB 的背景图和 BGM 可导入，文件哈希与原文件一致；实际在 Terre 中选中并保存，重新打开仍引用正确，预览能显示或播放。
- 来源在计划后变化、目标同名、越界或空间不足时，拒绝或报告确切状态，不覆盖现有文件。
- 中断后可以检查实际磁盘和批次；计划重放不重复创建文件，其他现有写入与恢复用例继续通过。
- Windows 上测得的上限和开销有记录，并检查暂存文件不会误入交付产物。上述任何保护未通过，就保留原有上限，并把大素材留到后续版本。

## 6. 本版边界

- 不替代 Terre，不修改 WebGAL、Terre 或 Galcode 上游，不开发动画、角色或流程图编辑器，也不做小说自动改编。
- 不自动启动、遥控、预览或打包 Terre，不从外部下载游戏素材。
- 不把关闭标签、磁盘静止或等待几秒当作保存完成。用户明确交接、版本检查、备份和恢复仍是写入门槛。
- Windows + Codex 继续作为必验组合。DeepSeek Harness、macOS 和 Linux 兼容、其他导出目标及 npm 发布不作为 v0.2.0 的交付条件。

## 7. 贡献与验证

1. **先挑一个任务。** 在 GitHub Issue 里引用 NEXT 编号，说明你要解决的具体现象、预期结果和准备怎样验证。新增工具或改变写入、恢复协议之前，先讨论接口与失败行为。
2. **做小而可复查的改动。** 一个 PR 尽量对应一个问题。只提交源码、测试夹具、构建配置或公开文档；不要提交个人路径、用户游戏、密钥或调试记录。测试用工程与素材使用可公开的原创样本，或在测试中现场生成。
3. **按改动运行检查。** 下面是功能改动的完整本机检查。从全新克隆安装时使用 `npm ci`。仅修改文档时核对命令、链接和示例，不必为它额外写自动化测试。

   ```powershell
   npm ci
   npm run check
   npm test
   ```

4. **说清测试覆盖了什么。** 契约模拟可以证明错误结果和协议行为；真人 Terre 验收用来证明场景可编辑、素材可用、预览能运行。不要混记。PR 说明请写明改动前后、验证组合、结果及已知限制。
